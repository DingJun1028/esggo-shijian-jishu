# 11 · 系統化除錯（四階段找根因）

> 來源：Hermes Agent `systematic-debugging` 技能（v1.1.0）。
> 適用：任何技術問題——測試失敗、生產 bug、效能、建置失敗、整合問題。核心：先找根因再修，症狀修補是失敗。
> 與第 10 章 TDD 配套（修 bug 先寫失敗測試）、第 08 章 esggo 故障排除表互補。

## 0. 鐵律

```text
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```
沒完成 Phase 1 就不能提修法。

## 1. 回饋迴圈規則（The Feedback Loop Rule）

除錯的工作就是這個迴圈。讀碼構理論前，先建一個**緊**的命令：能對使用者「確切症狀」紅、bug 修好才綠、快、確定、可重複——不能只是「不崩潰」。難重現就花不成比例力氣建迴圈；沒紅色迴圈就猜是此技能要防的失敗模式。

## 2. 四階段（每階段完成才能進下一階）

### Phase 1：根因調查
1. **讀錯誤訊息**：別跳過；stack trace 讀完整；記行號、路徑、錯誤碼。
2. **建緊迴圈**：一命令能觸發確切症狀？對此 bug 失敗、修好才過？夠快可重跑？確定？
   建迴圈順序（由近到遠）：
   1. 失敗測試（達到 bug 的縫）2. curl 打 dev server 3. CLI 夾 fixture diff stdout 4. headless browser 斷言 DOM/console 5. 重播擷取 trace（HAR/queue/webhook）6. 丟棄式 harness 啟最小切片 7. property/fuzz loop 8. `git bisect run` 二分 9. 差分 loop（舊v新/兩config/兩provider）10. 人類在迴圈（最後手段）
   非確定性 bug：目標是提高重現率（跑 100 次 / 平行 / 加壓），50% flake 可debug，1% 通常不行。
3. **查近期變更**：`git log --oneline -10` / `git diff` / `git log -p --follow <file>`
4. **多組件蒐證**：API→service→DB 邊界各加 log（進/出/環境/狀態），跑一次看哪斷。
5. **追資料流**：壞值從哪來？一路向上追到源頭，在源頭修。

Phase 1 完成清單：錯誤讀懂 / 有紅色迴圈且跑過 / 確定或可重現 / 近期變更已查 / 證據蒐集 / 隔離到組件 / 根因假說可陳述可測。

### Phase 2：模式分析
0. **最小化重現**：迴圈紅了後，一次移除一個輸入/呼叫者/config/步驟，重跑；移到只剩承重部分為止。
1. 找**可運作**的同類程式碼。
2. 比對參考實作（**完整讀**，別略）。
3. 列差異（別假設「那不可能有關」）。
4. 理解依賴與假設。

### Phase 3：假說與驗證
1. 先列 **3–5 個可證偽假說**，按可能性 + 證偽成本排序；每個寫預測「若 X 是原因，則改/觀察 Y 會使 Z 發生」。
2. 最小驗證：只改一個變數；優先用 debugger/REPL（一個 breakpoint 勝十行 log）；加 log 用唯一前綴如 `[DEBUG-a4f2]` 便於一次搜乾淨。
3. 驗證後：成→Phase 4；敗→新假說，別疊加修。
4. 不懂就說「我不懂 X」，問人或研究。

### Phase 4：實作
1. **先寫失敗測試**（回歸測試，用第 10 章 TDD）。
2. **單點修根因**：一次一改，不順手重構、不綁重構。
3. 驗證：`pytest tests/test_x.py::test_regression -v` + 全測查回歸。
4. **三則規則**：修 <3 次→回 Phase 1 帶新資訊；≥3 次→**停，質疑架構**（每次修在不同處暴露新耦合 = 架構錯，非假說錯，先與使用者討論）。

## 3. 紅旗 — 出現就回 Phase 1

- 「先 quick fix 以後再查」/「試改 X 看有沒有用」/「一次改多個跑測試」/「跳過測試手動驗」/「大概是 X 我修」/「不懂但可能有效」/「列的是修法而非調查」/「再試一次（已試 2+）」/「每次修在不同處冒新問題」

## 4. 常見合理化反駁

| 藉口 | 現實 |
|------|------|
| 「很簡單不用流程」 | 簡單也有根因，流程對簡單更快 |
| 「緊急沒時間」 | 系統化比亂試快 |
| 「先試這個再查」 | 第一次修定調，從一開始做對 |
| 「確認有效再寫測試」 | 沒測的修法留不住 |
| 「一次多修省時」 | 無法隔離哪個有效，還生新 bug |
| 「參考太長我改模式」 | 半懂必生 bug，完整讀 |
| 「看到問題我修」 | 看到症狀 ≠ 懂根因 |
| 「再試一次（2+ 敗）」 | 3+ 敗 = 架構問題，質疑模式別再修 |

## 5. 速查表

| 階段 | 關鍵動作 | 成功標準 |
|------|----------|----------|
| 1 根因 | 讀錯誤/重現/查變更/蒐證/追流 | 懂 WHAT 與 WHY |
| 2 模式 | 找可運作範例/比對/列差異 | 知哪裡不同 |
| 3 假說 | 列理論/最小驗/一次一變 | 確認或新假說 |
| 4 實作 | 回歸測/修根因/驗證 | bug 解、全測過 |

## 6. Hermes Agent 整合

- Phase 1 工具：`search_files`（找錯誤字串、追呼叫）、`read_file`（帶行號讀碼）、`terminal`（跑測/查 git/重現）、`web_search`/`web_extract`（查錯誤、讀庫文件）。
- 複雜多組件用 `delegate_task` 派調查子代理（goal 寫「調查原因，勿修」+ 完整錯誤 + 測試命令）。
- 與 TDD：修 bug 先寫重現失敗測試 → 系統化找根因 → 修根因（綠）→ 測試證明防回歸。

## 實際效益

系統化 15–30 分修好 vs 亂試 2–3 小時；首次修復率 95% vs 40%；幾乎不引入新 bug。
**無捷徑、不猜測，系統化恆勝。**
